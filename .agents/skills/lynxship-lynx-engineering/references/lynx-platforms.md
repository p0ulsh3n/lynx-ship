# Lynx platform and API map

Read the relevant official page before changing the corresponding adapter.
This is a routing map, not a copy of the framework manual.

## Pure Lynx and Rspeedy

Official references:

- [Quick Start](https://lynxjs.org/guide/start/quick-start)
- [Rspeedy CLI](https://lynxjs.org/4.0/rspeedy/cli.html)
- [Rspeedy configuration](https://lynxjs.org/api/rspeedy/rspeedy.config.html)
- [Lynx API/spec index](https://lynxjs.org/guide/spec.html)

Use `lynxship dev` for the Rspeedy dev server, QR output and live iteration.
Use `build` for a production bundle. `preview`, `inspect`, and `profile` are
diagnostic/build-tool workflows and do not create native store artifacts.
Always inspect the project's local `lynx.config.*` and package scripts before
assuming the output name or environment.

## Host embedding

Read [Integrate with Existing Apps](https://lynxjs.org/guide/start/integrate-with-existing-apps.html)
for the complete host contract. The host is responsible for initializing
Lynx, creating a `LynxView`, loading the bundle through a provider, and
providing platform services. A native host is not generated by Rspeedy itself.

The CLI host generators are intentionally minimal. They must not guess
application-specific permissions, native modules, push services, deep links,
entitlements, or store identities. Add those to the host only after reading
the platform and module documentation.

## Native libraries and Autolink

Read [Native Libraries and Autolink](https://lynxjs.org/guide/autolink) before
touching `lynx.lib.json`, Gradle Autolink plugins, CocoaPods Autolink, or
codegen. The official model is:

```text
npm package with lynx.lib.json
        ↓
Android Gradle / iOS CocoaPods Autolink
        ↓
generated registry
        ↓
LynxEnv initialization
        ↓
Elements + Native Modules + Services available to the host
```

Run the project's official codegen command from the library root. Verify both
platform declarations and generated files; do not hand-edit generated output
unless the upstream tool explicitly requires it.

## Native modules, elements and services

Use the [Lynx native development index](https://lynxjs.org/guide/spec.html)
and the current [Autolink documentation](https://lynxjs.org/guide/autolink)
to select the correct API. Confirm whether the capability is an Element,
Native Module, or Service; their lifecycle and registration contracts differ.
Keep platform-specific implementations explicit and test the JavaScript
facade against both the generated Android and iOS bindings when applicable.

## DevTool and runtime diagnostics

- [Lynx DevTool](https://lynxjs.org/guide/devtool)
- [Lynx debugging and error handling](https://lynxjs.org/next/guide/devtool/handle-errors.html)
- [Performance/trace index](https://lynxjs.org/guide/spec.html)

Use DevTool or native logs to prove a runtime issue. A successful Rspeedy
bundle only proves compilation; it does not prove native registration,
device permissions, platform services, or runtime behavior.

## OTA boundary

OTA is safe only when the installed native runtime can execute the new bundle
and assets. Before changing OTA logic, inspect the project's runtime
fingerprint inputs and the [Lynx native integration guide](https://lynxjs.org/guide/start/integrate-with-existing-apps.html).
Native code, permissions, linked libraries, host configuration and Autolink
registries are binary changes, not OTA-only changes.
