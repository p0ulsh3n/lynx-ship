# LynxShip and Sparkling: capability comparison

This is a factual engineering comparison, not a claim that one project is
faster without an identical benchmark. It records the public Sparkling APIs
and the LynxShip capabilities present in this repository on 2026-08-30.

## Scope

Sparkling is a native Lynx container and navigation SDK. Its public repository
describes the project as public beta: the architecture has been battle-tested
inside TikTok, while the public API surface and documentation are still
evolving. The latest public release visible on 2026-08-30 is `2.1.0-rc.36`
(pre-release); recent release notes include response-code alignment and Lynx
library autolinking. The comparison therefore uses the current public SDK/API
surface, not an older `rc.34` snapshot.
LynxShip includes that host layer plus a CLI, Expo/EAS integration, signed OTA
delivery, multi-tenant build services and platform adapters. The projects
therefore overlap at the container boundary but are not identical products.

## What “better” means for LynxShip

LynxShip should not win by copying undocumented internals. The target is a
stronger, measurable contract:

1. every public native capability has Android and iOS implementations or an
   explicit typed unsupported result;
2. every implementation is compiled by the matching platform CI job;
3. every lifecycle path has a unit test plus a native integration test;
4. every remote artifact is authenticated, content-addressed and rollbackable;
5. every cloud operation is tenant-scoped, observable and recoverable;
6. every performance claim is backed by a reproducible cold/warm benchmark;
7. every documented command works on the user's detected host platform.

## Advantages LynxShip now owns

These are intentional product differentiators, not claims about Sparkling's
undocumented internal systems: Expo/EAS integration, signed OTA with rollback,
cloud-build and worker contracts, tenant-scoped artifact handling, i18n/Intl
setup, realtime/notification contracts, multi-target CLI orchestration,
deterministic asset synchronization, and explicit native extension/update
callbacks. Each capability is implemented behind a separate package boundary
and covered by the repository gate where its effect is testable without a
device or hosted provider.

## Current proof boundary

The repository's local gate currently passes 284 tests, all workspace
typechecks, lint, builds, dashboard compilation and release checks. Android
native source contracts are checked, but Gradle compilation in this Windows
workspace is currently blocked by an unavailable configured JDK. Local
Windows execution cannot prove Xcode, iOS Simulator/device behavior, HarmonyOS
runtime behavior, a deployed PostgreSQL/Redis/R2 service, or production worker
isolation. Those are tracked as external acceptance gates rather than being
represented as completed features.
